# 问题修复反模式清单

以下是已发生过的错误模式，必须严格避免：

## 1. 反复调参反模式

**错误**：不理解根因，反复调魔法数字（`left - 20` → `left - 40` → `left - 15`），每次让用户验证。

**正确**：第一次失败后立即停下分析根因，追溯完整控制链路，理解精确变化原因和量后再改。

## 2. 影响范围失控反模式

**错误**：用户说"只改小屏"，结果修改公共逻辑导致大屏也受影响。

**正确**：修改前画清分支路径图，用条件判断严格限定生效范围，改后检查所有相关场景。

## 3. 自创等价逻辑反模式

**错误**：项目已有 `appScreenSize` 状态变量，却用 `document.body.clientWidth <= 720` 重新创造判断。

**正确**：复用已有状态源，保持单一数据源。确实需要新建判断时，向用户说明为什么不能复用。

## 4. 跳过根因分析反模式

**错误**：看到"间距小了"直接增大间距值，不分析为什么间距会变小。

**正确**：先问"为什么"再问"怎么改"。追溯完整链路：触发条件 → 状态变化 → 样式变化 → 视觉表现。修复针对根因而非表象。

## 5. 改动范围越界反模式

**错误**：用户限定了特定范围，却同时修改了范围外的文件。

**正确**：修改前列出完整文件清单与用户确认，严格按范围操作。范围外有类似问题也不"顺手"修改，告知用户后由用户决定。

## 6. 误解用户指令反模式

**错误**：用户说"逐字稿的不要动"，理解为"回退改动"，实际意思是"保留改动不再修改"。

**正确**：遇到"不要动"/"别改了"/"不用管"时先确认："您是希望保留当前改动不再修改，还是回退到修改前的状态？"

## 7. 优化范围失控反模式

**错误**：用户要求"优化本次改动的代码"，却把已有旧代码也一并优化。

**正确**：`git diff` 明确本次新增/修改范围，优化严格限定在 diff 内。已有代码有优化空间时单独建议，由用户决定。

## 8. JS/CSS 断点不一致反模式

**错误**：JS 断点和 CSS 断点阈值不一致，直接用 JS 枚举硬编码映射 CSS 行为。

**正确**：用 `getComputedStyle` 直接读取 CSS 变量实际值。如必须用 JS 判断，先完整列出两套断点阈值分析边界差异。

## 9. 优化时破坏 DOM 获取时序反模式

**错误**：优化代码时将 `document.getElementById` 从回调内部提到 `useEffect` 顶部，effect 执行时 DOM 未挂载 → 获取 `null` → 后续所有回调因闭包捕获 `null` 而失效。

**正确**：

- DOM 查询需要每次回调获取最新引用时，**必须放在回调内部**
- 唯一例外是用于注册 `ResizeObserver` 的一次性调用（但仅用于注册，不用于计算）
- 优化前必须分析执行时序：effect 执行时 DOM 是否已挂载？回调是否需要最新引用？
- **优化核心原则**：不改变代码行为，只改善代码表达。改变执行时序或闭包捕获的不是优化，是破坏。
