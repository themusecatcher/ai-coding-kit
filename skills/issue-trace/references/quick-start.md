# issue-trace 快速触发指南

> 📌 **本文档定位**：人类导航/速查（与 SKILL.md 角色互补）。
> SKILL.md 是 AI 运行时入口（含完整规则+反模式+执行细节），本文档是**面向用户的 1 分钟速查卡**。
> 触发关键词/不触发场景/工作流的**单一权威源在 `~/.codebuddy/skills/issue-trace/SKILL.md`**，本文档不重复维护，仅做导航。

---

## 🎯 一句话定位

**纯分析阶段，根因未定/未决定要修**时使用。看完输出由用户决定是否进入修复流程。

## ⚡ 命令速查

| 命令 | 快捷 | 说明 |
|------|------|------|
| `trace` | `t` | 完整 5 步分析流程 |
| `trace --quick` | `t -q` | 轻量模式：直接给结论 |
| `trace --chain` | `t -c` | 链路模式：侧重跨项目调用链 |
| `trace --suspects` | `t -s` | 仅嫌疑点列表，暂不深入 |

**示例**：
```
trace 为什么 Avatar 组件在中文环境下显示英文
t -c ShareModal 的完整调用链
t -s 详情页偶现白屏
```

## 🚦 与其他 skill 的边界

| skill | 入口信号 | 核心动作 | 是否进编码 |
|-------|---------|---------|:---------:|
| **issue-trace** | 描述现象/想追溯调用链/想定位根因 | 嫌疑点拆解 → 跨项目源码追溯 → 根因定论 | ❌ 仅分析 |
| **dev-flow** | 已确定要修/开发/优化 | 完整研究→方案→编码→交付 | ✅ 完整开发流程 |
| **bugfix-skill** | 任务平台 bug 链接 + 明确要修 | 任务平台 bug 修复闭环 | ✅ 修复+MR |

**触发优先级**（与 `rules/AI行为规范.mdc` 第 6 条对齐）：
```
用户显式指定 dev-flow
  > dev-flow 收尾模式
  > dev-flow 开发/修复/优化信号
  > 活跃流程恢复
  > issue-trace 根因诊断  ← 这一层
  > 普通对话
```

## 🔑 触发关键词速查（5 大类）

> 完整清单见 SKILL.md §「触发规则」（权威源）；本表仅做高频词速记。

| 类别 | 高频示例（任一命中即触发） |
|------|----------|
| **根因动词** | 排查根因、定位根因、分析根因、找根因、根因定位、根因分析 |
| **深度动词** | 深度分析、深入分析、深挖、深究、彻查、追溯、追踪、`trace 一下` |
| **追问句式** | 为什么会这样、这个值从哪来、这个参数为什么、这段逻辑怎么走的 |
| **链路追问** | 调用链是怎样的、整个流程是什么、完整调用链、跨项目分析、依赖追溯 |
| **嫌疑句式** | 问题在哪、嫌疑点、问题表象、表面看是 XX 但、看起来像 XX 的问题 |

## 🚫 不触发场景（避免误抢入口）

| 场景 | 应该走 | 原因 |
|------|--------|------|
| 用户说"帮我修这个 bug"+ 任务平台 bug 链接 | bugfix-skill | 已决定要修 |
| 用户说"开发 XX 功能"/"加个新功能" | dev-flow | 进入开发流程 |
| 用户问"这个函数怎么用" | 普通对话 | 简单咨询 |
| 用户元讨论 issue-trace 自身规则 | 普通对话 | 元讨论例外 |

## 📋 典型触发示例

✅ **应该触发 issue-trace**：

- 「企管后台中文环境时鼠标悬浮头像，活动空间为什么展示英文？」
- 「这个值从哪传过来的，帮我深度追溯一下」
- 「表面看是 UI 问题，但实际可能是接口问题，帮我定位根因」
- 「`useUserCard` Hook 里 `space.name` 字段从哪来的？整个调用链怎样？」
- 「list-component 里 Avatar 组件的 lang 参数追溯到 base-project 是怎么走的？」

❌ **不应触发**（即使有"分析"字样）：

- 「分析这个需求」→ requirement-intake
- 「修复这个登录问题」→ dev-flow（已决定要修）
- 「帮我看看 任务平台-12345 这个 bug」→ bugfix-skill（任务平台 修复入口）

## 🔄 工作流（5 步法概览）

> 完整执行细节见 SKILL.md §「工作流程（5 步法，强制顺序）」。

```
Step 1：现象输入解析
   ↓ 还原问题表象（环境/操作/期望 vs 实际）
Step 2：嫌疑点拆解（≥2 条，强制）
   ↓ 列出多个假设，避免单线思维
Step 3：反向追溯（核心，强制走『跨项目分析 reflex 三步法』）
   ↓ 本地优先 → 分支感知 → 命中读源码 / 未命中 4 选项
Step 4：根因定论
   ↓ 一句话结论 + 证据链
Step 5：输出格式（统一模板）
   • 根因定论 / 完整调用链（ASCII 树）/ 关键代码位置 / 证据链 / 治本治标双修复建议
```

## 🛡️ 物理门控（输出报告前必跑）

| 脚本 | 用途 | 退出码 |
|------|------|:---:|
| `scripts/trace-depth-check.sh` | 调用方追溯深度（wrapper import 是否同时给出实现位置）| 0 通过 / 1 断链 |
| `scripts/code-block-purity-check.sh` | 代码块原文一致性（防止 LLM 自创评价性注释）| 0 通过 / 1 污染 |

> 任一脚本退出码非 0 → 必须先修报告再重跑，禁止把不合格内容输出给用户。
