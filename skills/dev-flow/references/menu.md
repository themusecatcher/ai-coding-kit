# dev:ask — 全功能交互式菜单

## 一、路由声明

- **加载方式**：SKILL.md 触发 → `read_file("references/menu.md")`
- **不进入步骤流程**：不输出步骤完成标记 JSON，不写入工作上下文，不进入 dev-flow 步骤链
- **交互协议**：每一级菜单必须遵守"双重展示"规则：
  1. 先输出 Markdown 选项表格
  2. 再调用 `ask_followup_question` 弹出交互式选项
  3. 表格行数与 options 数组长度严格一致
  4. 编号一致

## 二、状态感知（每次加载时执行，必须）

以下 4 项检测在加载本文件后、弹出主菜单前执行，结果用于决定菜单选项的显示/隐藏：

### 检测清单

| # | 检测项 | 命令 | 用途 |
| --- | -------- | ------ | ------ |
| S1 | 活跃流程存在 | `ls ~/.codebuddy/working-context/.active-flows/*.flow 2>/dev/null` | 决定 B1/B4/B5 是否显示 |
| S2 | 已完成工作上下文 | `ls ~/.codebuddy/working-context/*.md 2>/dev/null` + grep `status: (completed\|testing\|delivered)` | 决定 B2/B3 是否显示 |
| S3 | 在 git 仓库中 | `git rev-parse --git-dir 2>/dev/null` | 部分选项的前提 |
| S4 | 当前分支 | `git branch --show-current 2>/dev/null` | B2/B3 匹配精度 |

### 结果处理

- 无可用选项时：**不显示该选项**（而非灰显），菜单保持简洁
- S1 命中时：一级 B 菜单标注 `[🔴 有活跃流程]`
- S2 命中时：一级 B 菜单标注 `[🟢 有已完成需求]`
- S1 和 S2 均未命中：一级 B 菜单标注 `[⚪ 无相关状态]`

## 三、一级菜单

> 一级菜单始终显示全部 6 个入口，状态徽标根据 §二 检测结果动态更新。

### 主菜单定义

| 选项 | 名称 | 状态徽标 | 进入 |
| :---: | ------ | --------- | ------ |
| A | 🚀 开始新的开发任务 | — | → §四-A |
| B | 🔄 继续已有需求 / 修复问题 | `{动态}` | → §四-B |
| C | 📝 同步文档与知识管理 | — | → §四-C |
| D | 📊 查看状态、度量与可视化 | — | → §四-D |
| E | 🛠 工具：项目接入、流程图、帮助 | — | → §四-E |
| F | ❓ 场景向导（不确定该用什么？） | — | → §四-F |

### 交互指令

**必须**先输出以下表格，再立即调用 `ask_followup_question`：

```text
选项 A：🚀 开始新的开发任务
选项 B：🔄 继续已有需求 / 修复问题 {S1/S2 徽标}
选项 C：📝 同步文档与知识管理
选项 D：📊 查看状态、度量与可视化
选项 E：🛠 工具：项目接入、流程图、帮助
选项 F：❓ 场景向导（不确定该用什么？帮我判断）
```

**ask_followup_question 参数**：

- question: "请选择你要使用的功能："
- options: 6 个选项（与表格逐条对应）
- multiSelect: false

**交互指令**：

## 六、完成协议

dev:ask **不输出步骤完成标记 JSON**，不进入 dev-flow 步骤体系。

- **导航类**（A0/B0/C0/D0/E0/F0/F1e/F2d/F3c/F7e）：重新显示目标菜单（主菜单 §三 或 F 第一轮场景选择），**不执行任何命令**，不进入任何流程
- **即执行类**：执行命令后输出简短确认，如 `✅ 已执行 dev:status` + 命令结果
- **需输入→入流程类**：收集输入后进入 dev-flow 流程（加载 flow.md + 步骤链）
- **场景向导类**：推荐命令后执行，流程同上

不需要更新工作上下文，不需要写 .flow 文件。
