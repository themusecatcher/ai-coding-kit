# 用户验收流程（步骤 6B）

> 步骤 6A 自动化验证全部通过后，自动弹出决策选项触发。

## 决策选项（交互式）

6A 验证通过后，**必须使用 `ask_followup_question` 弹出交互式选项**：

```text
自动化验证已全部通过，是否需要进行用户验收？

```

| 选项 | 说明 |
| --- | --- |
| ⏭️ 跳过验收 | 自动化验证已通过，直接进入步骤 7 清理+Commit |
| 🔍 进行验收 | 我要亲自验收功能，请准备验收环境 |

**默认推荐**：跳过验收（排在第一位），降低简单任务的交互成本。

## 验收流程（用户选择「进行验收」时执行）

### 1. 生成验收清单

基于需求描述和执行计划，生成结构化验收清单：

```markdown

## 验收清单

| # | 验收场景 | 操作步骤 | 预期结果 | 需要 Mock/调试 |
| --- | --- | --- | --- | --- |
| 1 | {正常场景} | {具体操作} | {预期表现} | 是/否 |
| 2 | {边界场景} | {具体操作} | {预期表现} | 是/否 |
| 3 | {异常场景} | {具体操作} | {预期表现} | 是/否 |
```

- 覆盖正常流程、边界条件、异常场景三类
- 每个场景的操作步骤必须具体可执行，不能笼统描述

### 2. 注入调试代码 / Mock 数据

根据验收清单中标记「需要 Mock/调试」的场景：

- 添加临时调试代码（如 console 输出关键状态、临时 UI 标记）
- 注入 Mock 数据模拟不同场景（如空数据、大量数据、异常响应等）
- **所有调试代码/Mock 数据使用统一标记注释 `// [ACCEPTANCE-TEST]`**，便于步骤 7 清理
- 无需 Mock/调试的场景跳过此步

### 3. 引导用户验收

输出验收引导信息：

```markdown

## 验收引导

- **启动命令**：`{如 npm run start}`
- **访问地址**：`{如 http://localhost:3000/xxx}`
- **验收步骤**：按上方验收清单逐项操作

> 验收完成后请告诉我结果，我将继续推进流程。

```

### 4. 收集验收结果

用户验收完成后，**必须使用 `ask_followup_question` 弹出交互式选项**：

```text
验收完成，请选择结果：

```

| 选项 | 说明 |
| --- | --- |
| ✅ 验收通过 | 所有场景符合预期，进入步骤 7 |
| ⚠️ 部分问题 | 告诉我哪些场景有问题（回退步骤 5 修复） |
| ❌ 验收不通过 | 功能不符合预期，回退步骤 3 重新制定方案 |

## 验收后清理

无论验收结果如何，进入步骤 7 前必须清理所有 `// [ACCEPTANCE-TEST]` 标记的调试代码和 Mock 数据。

## 回退机制

| 验收结果 | 处理 |
| --- | --- |
| ✅ 验收通过 | 清理调试代码 → 进入步骤 7 |
| ⚠️ 部分问题 | 清理调试代码 → 回退步骤 5 修复 → 重新走 5.5 → 6A → 6B |
| ❌ 验收不通过 | 清理调试代码 → 回退步骤 3 重新制定方案 |
