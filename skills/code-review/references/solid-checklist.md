# SOLID 架构审查清单

> L3 多视角审查「🏗️ 架构健康度」视角加载此文件。
> 审查改动代码是否违反 SOLID 原则，以及是否存在常见代码臭味。

## SOLID 原则检查

### SRP 单一职责

- [ ] 文件/模块是否承载了不相关的职责（如 HTTP 处理 + 业务逻辑 + DB 操作混在一起）
- [ ] 函数是否编排了多个不相关的步骤
- [ ] 是否存在"上帝对象"——了解系统太多细节的大类/模块
- **核心问题**："这个模块因什么唯一原因而变更？"

### OCP 开闭原则

- [ ] 新增行为是否需要修改多处 switch/if 分支
- [ ] 功能增长是否需要修改核心逻辑而非扩展
- [ ] 是否缺少插件/策略/钩子等扩展点
- **核心问题**："能否在不修改现有代码的情况下新增一种变体？"

### LSP 里氏替换

- [ ] 子类/实现是否检查了具体类型或对基类方法抛异常
- [ ] 重写方法是否削弱了前置条件或加强了后置条件
- [ ] 子类是否忽略或空实现父类行为
- **核心问题**："能否替换任何子类而调用者无感知？"

### ISP 接口隔离

- [ ] 接口是否包含大量方法，但大多数实现者只用到其中几个
- [ ] 调用方是否为了窄需求而依赖宽接口
- [ ] 是否存在接口方法的空/桩实现
- **核心问题**："所有实现者是否使用了所有方法？"

### DIP 依赖倒置

- [ ] 高层逻辑是否直接依赖具体的 IO/存储/网络类型
- [ ] 是否硬编码实现而非注入抽象
- [ ] import 链是否将业务逻辑耦合到基础设施
- **核心问题**："能否在不修改业务逻辑的情况下替换实现？"

## 常见代码臭味

| 臭味 | 识别信号 |
|------|---------|
| **过长函数** | 函数超 30 行，多层嵌套 |
| **特性嫉妒** | 方法使用其他类/模块的数据多于自身数据 |
| **数据泥团** | 同一组参数在多处反复传递 |
| **基本类型偏执** | 用字符串/数字代替领域类型 |
| **霰弹式修改** | 一次变更需要编辑多个文件 |
| **发散式变化** | 一个文件因多个不相关原因变更 |
| **死代码** | 不可达或从未调用的代码 |
| **投机泛化** | 为假设的未来需求创建的抽象 |
| **魔法数/魔法字符串** | 硬编码值未使用命名常量 |

## 重构启发式规则

1. **按职责拆分，而非按大小** — 小文件也可能违反 SRP
2. **仅在需要时引入抽象** — 等待第二个使用场景再抽象
3. **保持重构增量化** — 先隔离行为再移动
4. **先保留行为** — 重构前先补充测试
5. **按意图命名** — 如果命名困难，可能抽象本身有问题
6. **组合优于继承** — 继承创造紧耦合
7. **让非法状态不可表示** — 用类型系统强制约束

## 移除候选 + 迭代计划

审查时同时识别可删除/可清理的代码：

### 可立即安全删除

| 字段 | 内容 |
|------|------|
| **位置** | `` `相对路径` `` L行号 |
| **原因** | 为何应删除 |
| **证据** | 无引用 / 死特性开关 / 废弃 API |
| **影响** | 无 / 低 — 无活跃消费者 |
| **删除步骤** | 1. 删除代码 2. 删除测试 3. 清理配置 |
| **验证** | 运行测试、检查无运行时错误、监控日志 |

> 📌 「位置」字段必须按 `~/.codebuddy/rules/AI行为规范.mdc` 的「文件/代码位置引用」规范使用可点击链接（行号区间用 `#L起-L止` 锚点）。

### 延迟删除（需计划）

| 字段 | 内容 |
|------|------|
| **位置** | `` `相对路径` `` L行号 |
| **延迟原因** | 有活跃消费者 / 需要迁移 / 需要审批 |
| **前置条件** | 特性开关关闭 2 周 / 遥测显示 0 用量 |
| **迁移计划** | 消费者迁移步骤 |
| **时间线** | 目标日期或迭代 |
| **Owner** | 负责人/团队 |
| **回滚方案** | 如发现问题如何恢复 |

### 删除前检查清单

- [ ] 搜索了代码库中所有引用（rg / grep）
- [ ] 检查了动态/反射调用
- [ ] 确认无外部消费者（API / SDK / 文档）
- [ ] 审查了特性开关遥测数据（如适用）
- [ ] 更新/删除了相关测试
- [ ] 更新了相关文档
- [ ] 通知了团队（如为共享代码）
