# 交付前精修与三方一致性规范（refine-spec）

> 定位：dev-comp **阶段 5 第 5 步（清除对照 + 交付前精修）**的唯一权威规范源。阶段 5 收尾按需加载。
> 触发：**每次组件开发收尾必做**（含增量完善轮次）。确定性项已下沉 `scripts/validate-component.sh`（`C5` + `G1-G5`），模糊项由本文件定义判定标准、人工勾销。
> 与项目规范关系：与 `{PROJECT_ROOT}/development/*.md` 冲突时**以项目规范为准**，并立即回填本文件（双向引用，见 `rules/按需-Skill设计-跨文件协作.mdc` §2.1）。

---

## 0. 为什么要这一步（三次实践复盘）

| # | 问题 | 典型形态 |
|:--:|:--|:--|
| 1 | **品牌痕迹随内容沉淀** | 演示页对照清了，但组件注释里的「对齐 antd 口径」「参考 naive 实现」被提交进仓库 |
| 2 | **组件源码增量劣化** | 注释越写越多（复述代码）、新 Prop 一律追加到 `interface Props` 末尾，`modelValue` 与 `spaceProps` 相邻 |
| 3 | **演示与文档漂移** | 演示用例越补越乱（新用例直接 append 末尾）、布局不统一；docs 是手工派生副本，单边改动必然滞后 |

因此本步一次性完成三件事，**顺序不可颠倒**：

```
清品牌（§1）  →  精修三处产物（§2 源码 / §3 源码 / §4 演示页）  →  三方对账（§5）
   先清          再修（各处内部一致）                                后对（三方相互一致）
```

> ⚠️ 第 5 步位于**浏览器实测验收之后**：对照分区（antdv/naive 真身）是验收手段，验收完才能清除；精修属实质改动，因此本步末必须再复验一次（§6）。

## 1. 品牌信息清除（红线）

> 用户要求：交付物中**不得残留** antdv / naiveui 两个参考库的任何品牌内容与信息（代码 + 注释 + 文案）。

### 1.1 禁用词表

| 类别 | 须清除的形态 |
|:--|:--|
| 库名 / 品牌 | `antdv`、`antd`、`ant-design-vue`、`Ant Design Vue`、`naive`、`naive-ui`、`Naive UI` |
| 组件标签 | `<a-auto-complete>` 等 `<a-xxx>` antdv 真身标签、`<NTooltip>` 等 naive 组件标签 |
| 变量 / 类名残留 | `avalue*` / `aoptions*`（对照期数据变量）、`antdTheme`、`ant-xxx` class 前缀 |
| 注释来源标注 | 「对齐 antd 口径」「antd 没有 xx」「参考 naive 的 xx 实现」「仿 antd」等一切以品牌名作依据说明的句子 |

### 1.2 唯一例外（2026-09-22 实测确认，可调整）

`@ant-design/*` **基础包**（图标 `@ant-design/icons-vue`、色板 `@ant-design/colors` 等）**不算品牌残留**：

- 它们是项目 `devDependencies` 既有依赖，与 antdv（组件库 `ant-design-vue`）是**不同包**；
- 实测：`src/views/` 下 32 个演示页统一 import `@ant-design/icons-vue` 提供图标，属基础设施而非对照痕迹；
- 脚本按行过滤 `@ant-design/(icons-vue|colors)`。若要连图标包一并清理，须先确认替代方案再改本文件与脚本（§7）。

### 1.3 扫描范围与口径（最小入侵 + 兼容「分批开发/分批提交」）

> ⚠️ **分批提交场景（用户 2026-09-22 补充）**：组件常分批开发、每批完成后即提交一次。**只在最后收尾查看工作区是不准确的**——前面几批的品牌残留已经在 commit 里，`git diff HEAD` 看不到。因此口径必须同时覆盖「**已提交的本分支改动**」与「**未提交的工作区改动**」。

**两段扫描口径**（缺一不可）：

| # | 对象 | 取行方式 |
|:--:|:--|:--|
| ① | 本分支**净改动**（基点 → **当前工作区**） | `git diff <base> -U0` 的 `+` 行——一次覆盖「**已提交的每一批** + **未提交的工作区**」 |
| ② | **未跟踪新增文件** | **全文**扫描（含行号） |

> ⚠️ 为何用「基点 ↔ **当前工作区**」而不是分别扫「基点↔HEAD」+「HEAD↔工作区」：后者会把「已提交、但已在工作区删掉」的行算作残留（**假阳性**）——那属于已修复、即将随提交消失的内容。净改动口径 =「本分支**最终**引入的行」，语义更准。
>
> **附注机制**：净改动为 0 时会再查一次「已提交批次（base...HEAD）」——若仍有残留，说明**工作区已清除但删除尚未提交**，脚本给 **WARN** 提醒「必须随本次 commit 提交，否则复活」（与 `components.d.ts` 幽灵声明同理）。

**base（分支基点）解析优先级**：`--base <ref>` 参数 → 工作上下文 frontmatter `base_ref` → `git merge-base origin/main|origin/master|main|master HEAD` 自动探测 → 均失败则退化为「工作区 vs HEAD」并 **WARN**（分批提交场景会漏检）。

**覆盖范围**（用户口径「开发过程中的所有相关改动」）：

| 范围 | 说明 |
|:--|:--|
| `components/` | 组件源码 / 子组件 / `index.ts` / 样式 |
| `src/` | 演示页 + 演示数据 |
| **`docs/`** | ⭐ **组件文档 + 周边文档（`changelog.md` / `features.md` / `index.md`）+ vitepress 配置**——**docs 内容必须清除干净**（用户 2026-09-22 明确） |
| `types/` / `tests/` | 类型声明 / 单测注释 |
| 根级 | `README.md` / `README.zh-CN.md` / `CHANGELOG*` |

**豁免（不是残留，是必需配置 / 生成物）**：

| 类别 | 路径 |
|:--|:--|
| 基础设施 | `package.json`、`pnpm-lock.yaml`、`components.d.ts`、`vite.config.ts`、`tsconfig*`、`.eslintrc*` |
| 构建/生成产物 | `node_modules/`、`dist/`、`lib/`、`es/`、`coverage/`、`.temp/`（含 `docs/.vitepress/.temp/`） |
| 贡献者规范目录 | `development/`——面向贡献者的设计规范，**允许**提及参考库（如 `component-design.md` 说明「对齐 XX 的结构」），不属残留 |

> ⚠️ **词表 ↔ 脚本必须同步**：本词表与 `scripts/validate-component.sh` 的 `BRAND_PAT` 严格对应。实测教训（2026-09-22 自查）：脚本最初只写 `antdv`，**漏检单写 `antd`** 的注释（存量高频形态「对齐 antd 口径」，`ant-[a-z]+` 也匹配不到）——已修，两种写法都覆盖。

> 存量组件（如 `components/select/Select.vue`）历史注释中大量存在「antd 口径」写法——**本轮不追改**（超出本次改动范围、违反最小入侵）；如需全库清理应另立专项（见 §7 待办）。

### 1.4 处置规则：**删除优先**（用户 2026-09-22 决策）

#### A 类 · 品牌对比 / 差异说明 → **直接删除，不保留**

**凡是以参考库为参照系来说明「差异 / 不覆盖 / 命名对齐 / 破坏性变更」的内容，一律整段删除**，不做「改写成与官方实现相比」这类中性化保留：

| ❌ 须整段删除的形态 | 处置 |
|:--|:--|
| docs 章节/段落：「⚠️ 与 [Ant Design Vue](https://www.antdv.com/…) 的差异：官网的 `dropdownStyle` / `getPopupContainer` 本库有意不覆盖…」 | **整段删除**（含链接与 bullet 列表） |
| changelog 条目：「**破坏性变更**：属性命名对齐 [Ant Design Vue]…」 | **删除品牌指代**，只保留本项目自身的变更事实（`search` 更名 `showSearch` 等），不解释「对齐了谁」 |
| 演示页对照分区（`<h3>antd 官网组件</h3>` + 真身组件 + 数据） | 整个分区删除（`flow.md` 阶段 5 第 5 步 a 项） |
| 注释：「与 antd 不同的是本项目 slot 优先」 | 删除品牌指代，只留项目约定：`// 本项目统一「插槽优先于 prop」` |

> 删除后**不需要**补偿性改写；若该「差异原因」对维护有价值，写进 `devlog` / 工作上下文「决策记录」，**不进仓库**。

#### B 类 · 注释中的来源标注 → 删除优先，必要时去品牌化

| ❌ 残留写法 | ✅ 处置 |
|:--|:--|
| `// 对齐 antd 口径` | **直接删**——本项目口径即权威，无需声明它来自哪里 |
| `// 参考 naive 的 xxx 算法` | `// 采用 xxx 算法（决策记录见 devlog）` |
| `/** 对齐 antd 的 LabeledValue */` | `/** labelInValue 打开时的 value 对象形态 */` |
| `// antd 没有「已选项标签缓存」，若清空 options…` | 删除品牌指代，保留本项目行为说明 |

> ⚠️ **规范冲突修正**：`reference-sources.md` 旧表述「实现可复用 naive 的某段算法（在代码注释注明来源）」**已废**。新口径：**代码注释不写品牌来源**；来源与决策理由写 `devlog` / 工作上下文「决策记录」。该文件已同步修正。

## 2. 组件源码注释精修（`components/{组件名}/`）

### 2.1 三层结构（逐层检查）

| 层级 | 位置 | 要求 |
|:--|:--|:--|
| 组件级 | `<script setup>` 起首 / SFC 顶部 | 一句话说清「组件做什么 + 关键约束」，**≤3 行** |
| 字段级 | `interface Props` / `{组件名}Slots` **每个字段行尾** | 中文注释；说明**取值含义 + 生效条件**（如 `// 仅当 dynamic: true 时生效`） |
| 分支级 | 复杂判断 / 兜底 / 兼容分支上方 | 说明**为什么**这么写、边界是什么（不是复述这行做了什么） |

### 2.2 该写 vs 该删

| ✅ 保留（有信息增量） | ❌ 删除（无信息增量） |
|:--|:--|
| 非直觉行为的原因（如「插槽优先于 prop，故此处先判 slots」） | 复述代码（`// 设置 loading 为 true`） |
| 边界取值语义（`0` / `''` / 空数组 / falsy 时的表现） | 品牌与来源标注（§1.4） |
| 易错点 / 坑位提醒（与项目约定相关） | **过期注释**（代码已改、注释未改——最容易骗人的一类） |
| 主题注入、slot 优先等**项目级约定**的落点说明 | 大段原理解释（>3 行 → 移入 devlog / 工作上下文） |

### 2.3 判定标准

> **读者 5 秒内能回答：这段在做什么？为什么这么做？**

- 能 → **不写**（注释不是越多越好）；
- 不能 → 补/改；
- 警戒线：出现「整段无一注释的复杂分支」或「行行都有注释的流水账」，两者都要重写。

## 3. Props 属性排序

> 事故形态：增量开发时新 prop 直接追加到 `interface Props` 末尾 → `modelValue` 与 `spaceProps` 相邻，语义割裂、阅读跳跃。

### 3.1 六段式分组顺序（从前到后）

| 序 | 段 | 典型字段 |
|:--:|:--|:--|
| 1 | 双向绑定 / 受控核心 | `modelValue`、`open`、`show`、`visible`、`current`、`checked` |
| 2 | 内容与数据源 | `options`、`items`、`data`、`value`、`src`、`content`、`label` |
| 3 | 形态与外观 | `type`、`shape`、`size`、`mode`、`variant`、`placement`、`color`、`alt` |
| 4 | 状态与反馈 | `disabled`、`loading`、`status`、`bordered`、`readonly`、`href`/`target` |
| 5 | 行为与交互 | `closable`、`maskClosable`、`trigger`、`delay`、`showSearch`、`dynamic`、`autofocus` |
| 6 | 进阶 / 透传 | `class`/`style`/`rootClass`、`virtual`、`getPopupContainer`、自定义渲染 prop、`xxxProps` 透传 |

### 3.2 段内规则（不强制字母序）

1. **段内按语义相关性自然排列**（相关性高的相邻，如 `minDate`/`maxDate`、`start`/`end`、`A` 与「仅当 A 开启才生效的 B」）。
2. **不强制字母序**——实测项目既有组件（`tag.md` / `components/tag/Tag.vue` 等）源码与文档表均为**语义序而非字母序**，强推字母序会破坏语义相邻性、并与既有惯例冲突。
3. **增量添加 = 插入所属语义段**，❌ 禁止直接追加到末尾。
   → **脚本保「一致」、人工保「合理」**：脚本（`G2`）只能校验「源码与 docs 同序」，是否呈「合理排列」由人工按本节点检。

### 3.3 硬约束（可校验）

> **源码 `interface Props` 字段顺序 ≡ `docs/guide/components/{组件名}.md` 中 `## APIs` → `### {组件名}` 表的行顺序**（逐项同序）。

- 实测依据：项目既有 `tag.md` 的 API 表行序与 `Tag.vue` 的 `interface Props` 字段序**完全一致** → 该一致性本就是项目隐含惯例，本规范只是显式化 + 脚本化。
- docs 表是**用户阅读界面**，两边必须同步；顺序不一致即 **FAIL**（脚本 `G2`）。
- 重排必然**同时改两处**；`Slots` / `Events` / `Methods` 表顺序也需与源码 `defineSlots` / `defineEmits` / `defineExpose` 定义顺序一致（如有）。
- **复合组件支持**（2026-09-22 自查补充）：`G2` 按 `.vue` 文件（含一层子目录）**逐一**与 docs 中同名 `### {子组件名}` API 表比对（如 `Dropdown.vue ↔ ### Dropdown`、`DropdownButton.vue ↔ ### DropdownButton`）；单文件组件用 `### {组件名}`。docs 中同名的 `### Xxx` 会在 Slots / Methods 区重复出现，脚本**限定在 `## APIs` 之后**取表，避免取错。
- ⚠️ **脚本判定为启发式（半确定性）**：`G2` 从 `interface Props { … }` 块提取字段序、从 API 表首列提取表序。以下情况报 **SKIP/WARN 而非误判 FAIL**，属设计使然——① 声明写作 `export interface Props extends Xxx {`（不匹配 `Props {`）或跨行；② 字段类型为跨行对象字面量（内层键可能被误提取）；③ 表首列用 `v-model:value`、`<Tag color="cyan">v-model</Tag>` 等非裸标识符写法（匹配率 <60% 报 WARN）；④ 子组件在 docs 中无独立 `### Xxx` 小节。**出现 SKIP/WARN 时必须人工比对**——脚本保「一致」，人工保「合理」。
- 补充约定：docs API 表**未列出**的源码 prop（多为 `v-model:value` 命名差异）只出 WARN 提示，**不影响顺序一致性的 PASS 结论**。

### 3.4 反例 → 正例

```ts
// ❌ 增量追加形态（语义割裂：新 prop 被追到末尾，与前段无关）
export interface Props {
  modelValue?: string
  src?: string
  loading?: boolean
  spaceProps?: SpaceProps  // ← 新加的，被追到末尾
  closable?: boolean
}
```

```ts
// ✅ 六段式分组 + 段内语义相邻（按规范重排后，docs API 表同步成同一顺序）
export interface Props {
  modelValue?: string                    // 1 双向绑定

  src?: string                           // 2 内容与数据源

  size?: 'small' | 'middle' | 'large'    // 3 形态与外观

  loading?: boolean                      // 4 状态与反馈

  closable?: boolean                     // 5 行为与交互

  spaceProps?: SpaceProps                // 6 进阶 / 透传
}
```

## 4. 演示用例精修（排序 + 布局）

> 对象：`src/views/{组件名}/Index.vue`（**用例的唯一权威源**，docs 是派生副本）。

### 4.1 排列顺序

| 规则 | 说明 |
|:--|:--|
| 官网用例**保序** | 完整复制官网全部展示用例并**保持官网原序**（阶段 3 既定规则，不因增量而变） |
| 新增官网用例 | 插入其**官网原序位置**——❌ 不是追加到末尾 |
| 项目特有用例 | 统一置于末尾「项目特有场景」区块内；同主题（主题切换 / 边界态）相邻 |
| ❌ 反例 | 新用例一律 append 末尾 → 「基础用法」后面跟着「极端边界」，顺序与官网脱节 |

### 4.2 布局方式

| 场景 | 布局 |
|:--|:--|
| 单一示例 | 整块排布 |
| 2+ 同构示例（多尺寸 / 多类型 / 左右对照） | `demo-row` + `demo-col` 并排（沿用项目既有容器 class，见同类演示页） |
| **需交互的示例**（下拉 / 拖拽 / 浮层 / 可输入） | **单独全宽**，❌ 不与其它示例并排（避免遮挡、焦点争抢） |
| 长表格 / 大尺寸组件 | 全宽 |

**布局一致性红线**：**同类型用例的布局方式必须一致**（都并排 / 都整块），❌ 禁止同类用例一半并排一半整块。

### 4.3 每个分区的统一结构

```html
<h2 class="mt30 mb10">{用例标题}</h2>        <!-- 标题不带数字序号（F7） -->
<p class="mb10">{可选描述}</p>               <!-- 仅信息增量时添加；格式见 demo-description.md -->
{示例容器}                                    <!-- 布局按 §4.2 -->
```

- 描述规范（标题纯场景名 / 信息增量评估 / `<code>` 包裹范围）→ `demo-description.md`，本文件不重复。
- 精修演示用例后**必须立即同步 docs**（§5），❌ 禁止只改一边（`demo-description.md` §0 单一权威源原则）。

## 5. 三方一致性对照（源码 ↔ docs ↔ views）

### 5.1 对照矩阵（逐格勾销，❌ 项带处置）

| 维度 | 组件源码 `components/{名}/{Xxx}.vue` | 文档 `docs/guide/components/{名}.md` | 演示页 `src/views/{名}/Index.vue` | 校验 |
|:--|:--|:--|:--|:--|
| 用例数量 | — | `##` 用例标题数（剔除固定章节） | `<h2>` 数 | 脚本 `G4` |

## 7. 边界与待办

- **存量不追溯**：本次只处理「本分支**净改动新增行**（基点 → 当前工作区）+ 未跟踪新增文件全文」。存量组件的历史品牌注释（如 `Select.vue` 的「antd 口径」）**不在本轮范围**——如需全库清理，应另立专项任务（一次性扫描 `components/` + `src/views/` + `docs/`，产出清单后批量改写），避免与本次组件开发混在一个 commit。
- **依赖包豁免（已确认，非可调整项）**：`@ant-design/icons-vue` / `@ant-design/colors` 等 `@ant-design/*` 基础包**不需要清除**（用户 2026-09-22 明确）——它们是项目既有依赖，与参考库组件包 `ant-design-vue` 是不同包。
- **分批提交（必读）**：分批开发 → 分批提交时，收尾只看工作区会漏掉已提交批次。因此 ①**阶段 1 建分支后立即在工作上下文登记 `base_ref`**（`git merge-base origin/main HEAD`，分支基点）；②收尾跑 C5 时若输出 WARN「未解析到分支基点」，必须显式 `--base <ref>` 重跑，否则判定不完整。已合入主干的场景无法回溯（merge-base = HEAD），此时依赖工作上下文登记的历史 `base_ref`。
- **规律变更必须同步脚本**：本文件的词表 / 判定规则变更时，必须同步改 `scripts/validate-component.sh`（`C5` / `G2` / `G4` 实现）与 `checklists.md` §发布前配置项终检（规则变更只改文档 = 规则形同虚设）。
