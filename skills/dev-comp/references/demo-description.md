# 简介描述规范（演示页 + docs 同源）

> 本文件是「用例标题 + 简介描述」的**单一权威规范源**。阶段 3（演示页）/ 阶段 4（文档）按需加载。
> 背景：简介描述在演示页与 docs 两处独立维护，历史上因「无权威源约定 + 无同步机制」反复出现漂移（标题带 API 名、描述一刀切、误用不存在的组件、两边段落数不一致等）。本文件从根上约束。

---

## 0. 核心原则（红线）

**单一权威源 + 派生副本 + 改动即同步**：

1. **权威源 = 演示页** `src/views/{组件名}/Index.vue`（阶段 3 先建）。
2. **派生副本 = docs** `docs/guide/components/{组件名}.md`（阶段 4 从演示页逐字复制，仅代码标记转换）。
3. **任何改动先改权威源（演示页），再立即同步派生副本（docs）**；反向（用户指出 docs 问题）也必须回写演示页。**禁止单边修改**。
4. 阶段 5 验收用 grep 强制同源校验（见 §5）。

> 违反本原则是历史漂移的根因：每次只改一处，另一处必然滞后。

## 1. 标题规范

- **纯场景名，不带 API 属性名**。如 `键盘/悬浮回填`（而非 `键盘/悬浮回填（backfill）`）、`默认展开`（而非 `默认展开（defaultOpen）`）。
- 官网有的用例 → 用官网标题；官网无但 API 有的能力 → 自拟「能力描述」纯中文标题。
- 标题即用例名，API 属性名放描述或 API 表格，不进标题。

## 2. 描述添加条件（信息增量评估，逐条判断）

**仅在「标题/属性名无法表达 + 确有信息增量」时添加**。以下情况一律不加：

| 情况 | 示例 | 处置 |
|------|------|------|
| 标题/属性名自解释 | `禁用`、`关闭默认高亮首项`、`disabled` | 不加 |
| 描述与标题重复（同义改写） | 标题「默认展开」→ 描述「初始即展开面板」 | 不加（或只保留非重复的增量句） |
| **与已有段落重复（信息子集）** | 已有「键盘 ↑↓ 导航回填…按 Enter 确认、Esc 还原…悬浮回填」，又新增「回填后按 Enter 确认、Esc 还原」 | **不加**——新增段落是已有段落的子集，属双行冗余 |
| 属性名已简单明了 | `disabled` 这类 | 不加 |

**必须加**的增量类型（标题表达不出的信息）：

> 注：同一用例的描述可能**同时**含「与标题重复的句子」和「增量句子」——删前者、留后者。例：「默认展开」描述中的「初始即展开面板」是与标题重复的（删），「区别于受控 `open`，初始值生效后不受外部状态控制」是易混淆区分点（留）。

| 类型 | 示例 |
|------|------|
| 隐藏行为 | 下拉面板宽度「空间不足时自动调整对齐」 |
| 易混淆区分点 | 默认展开「区别于受控 `open`，初始值生效后不受外部状态控制」 |
| 组合键/配套交互 | 键盘回填「按 `Enter` 确认、`Esc` 还原」 |

### 2.1 多段描述专项自检（新增段落前强制执行）

**一个用例的描述可以是多段（多 `<p>`），但新增任何段落前必须执行本自检**——历史事故：已有完整描述后又补一句同义小段，形成双行冗余（`键盘/悬浮回填`，2026-08-19）。

```bash
# 第 1 步：定位用例章节范围（标题 → 下一个标题之间）
grep -n "<h2" src/views/{组件名}/Index.vue               # 演示页：找该用例标题行与下一个 <h2> 行
grep -nE "^## " docs/guide/components/{组件名}.md        # docs：找该用例标题行与下一个 ## 行
# 第 2 步：read_file 读取该范围，提取全部已有描述段落，逐字对比
# 第 3 步：判定新增段落是否「已被已有段落/标题完整包含（信息子集）」→ 是，不加
```

- **逐段判定子集**：新增段落的每个信息点（动作/条件/效果），逐个在已有段落中找对应句；全部命中 → 子集冗余，不加；有增量点 → 只保留增量部分（删掉重复句）。
- **先 grep 再动笔**：grep 该用例标题下的全部 `<p>`/段落（演示页与 docs 都要看，因两处同源），逐字对比后确认信息增量才写。
- **演示页和文档页同步审**：双行冗余经常是「先在一处补、复制到另一处」的连锁结果——两处必须同一步骤审查、同一结论、同步修改。
- **存量双行冗余的修复**（发现已有冗余时）：删除信息子集段、保留信息超集段（被包含的那段是冗余），演示页/docs 两边同步删、段落数保持一致——与「新增段落」对称，修复同样执行上述 grep 定位 + 两边同步。

## 3. 描述结构规范

- **段落数量两处一致**：演示页几个 `<p>`，docs 就几个段落（可「简述 + 详细」多段，但两边段数必须相同）。
- **代码标记**：
  - 演示页（`.vue`）：原生 `<code>` 标签。
  - docs（`.md`）：反引号 `` ` ``（渲染同为 `<code>` 元素）。
  - ⚠️ **禁止用 `<Text>` 等未确认存在的组件**——引用任何组件前先 `search_file` 确认项目内确实存在。
- **间距差异**（关键，易反向）：
  - docs（`.md`）：描述段落与组件之间**用 `<br/>` 间距**（markdown 段落不自动与后续组件拉开距离）。
  - 演示页（`.vue`）：描述用**目标项目既有的间距 class**（vue-amazing-ui 为 `mb10`），**无需 `<br/>`**（`<p>` 自带段落间距）。⚠️ `demo.tpl.vue` 骨架的 `.demo-desc` 是模板 scoped 占位样式，**落地到项目时替换为项目实际 class**，禁止照抄。
- **文本逐字一致**：两边除代码标记写法不同外，描述文字完全一致，不做同义改写。

## 4. 同步机制（改动即同步，禁止单边）

改完演示页描述后，**立即**执行：

```bash
# 从演示页取描述 → 与 docs 对应段落对比
grep -n "描述关键词" src/views/{组件名}/Index.vue
grep -n "描述关键词" docs/guide/components/{组件名}.md
```

两边文本（除 `<code>` ↔ 反引号）必须逐字一致；段落数一致；docs 有 `<br/>`、演示页无。

## 5. 同源验证命令（阶段 5 验收用）

```bash
# 抽一个描述关键词（用本组件实际的描述文案替换「描述关键词」），双向对比
grep -n "描述关键词" src/views/{组件名}/Index.vue docs/guide/components/{组件名}.md
# 断言：文本一致；.vue 用 <code>、.md 用反引号；.md 描述后有 <br/>、.vue 无
```

## 反模式清单（历史踩坑）

| 反模式 | 正确做法 |
|--------|---------|
| 标题写 `场景名（apiProp）` | 标题纯场景名，属性名进描述/API 表格 |
| 所有 API 用例都加描述 | 逐个做信息增量评估，自解释的不加 |
| **已有完整描述后又补一句同义小段（双行冗余）** | 新增段落前 grep 章节已有描述做子集判定，无增量不加（§2.1） |
| 演示页与 docs 分别独立编辑 | 先改演示页 → 立即 grep 同步 docs |
| docs 要 `<br/>`、误以为演示页也要 | docs 要 `<br/>`，演示页 `<p>` 自带间距不需要 |
| 精简描述时只改一边，段落数漂移 | 段落数两处强制一致，改一处同步另一处 |
| 用 `<Text code>` 等未确认组件 | 先 `search_file` 确认存在，否则用原生 `<code>` |
